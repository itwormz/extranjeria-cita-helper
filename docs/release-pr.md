# Выпуск релиза через PR

Один раз добавьте в GitHub Actions секрет репозитория `RELEASE_TAG_TOKEN`.
Подойдёт fine-grained PAT с доступом только к этому репозиторию и правом
Contents: Read and write. Владелец токена должен иметь право создавать
теги `v*`. GitHub запускает сборку по push тега, сделанному этим токеном.
Штатный токен workflow подавляет такой запуск.

В релизном PR:

1. Укажите стабильную версию одной строкой в `.github/release-version`,
   например `0.3.1`.
2. Добавьте текст для GitHub Release в раздел `## Unreleased` в
   `CHANGELOG.md`. Заголовок можно дополнить названием выпуска,
   например `## Unreleased — Улучшения поиска`.
3. Дождитесь обязательных проверок PR и смержите его в main.

Workflow перенесёт версию в `app/version.py`, `pyproject.toml` и
`uv.lock`, оформит раздел changelog и проверит метаданные. Затем он
создаст релизный коммит на основе смерженного main и отправит тег
на этот коммит. Так запись в защищённую ветку проходит через PR,
а стабильная версия попадает в исходники и пакеты релиза.

Сборка по тегу проверит пакеты, создаст контрольные суммы и
аттестации и опубликует релиз. Для обычного PR достаточно оставить
`.github/release-version` как есть. Локальные сборки используют версии
вида `0.3.0.dev2` и отдельные папки в `.local/builds`.

Если сборка упала после создания тега, откройте исходный запуск
Build desktop packages для этого тега и повторите упавшие задачи.
