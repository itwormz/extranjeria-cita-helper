# Бета-релиз SantaCita через PR

Репозиторий пока не переименовываем. Python остаётся в `main`. Эти инструкции относятся к будущей Rust-ветке `santacita-beta`; она создаётся из `codex/rust-port-plan`, когда текущие доработки завершены.

## Один раз

- Сохранить секрет `RELEASE_TAG_TOKEN`: fine-grained PAT с доступом к репозиторию и Contents: Read and write. Он используется для коммита подготовленных файлов и тега, чтобы GitHub запустил следующие проверки.
- Разрешить подготовительной автоматизации писать в `release/*` и создавать `v*` теги; настроить защиту `santacita-beta`.
- Оставить включённой неизменяемость релизов. Не переносить опубликованные теги и не заменять опубликованные пакеты.
- Сначала влить инфраструктуру обычным PR и запустить **Build SantaCita packages** вручную на Rust-ветке. Это не публикует релиз.

## Что готовит автор релиза

1. Создать `release/0.4.0-beta.1` от актуальной `santacita-beta` (для следующего релиза подставить новую версию).
2. Указать только номер версии в `.github/release-version`, без `v`.
3. Написать готовые заметки в `CHANGELOG.md`:

   ```markdown
   ## Unreleased — First SantaCita beta

   - Your final user-facing release notes.
   ```

   Этот текст попадёт на страницу релиза. Не оставлять черновые формулировки и перечень технических коммитов.

4. Отправить ветку. Запустить **Prepare or tag SantaCita release PR** через Actions с выбором этой `release/*` ветки. Workflow обновит `Cargo.toml`, версии workspace в `Cargo.lock`, `desktop-ui/package.json`, `desktop-ui/package-lock.json` и раздел CHANGELOG. Не редактировать эти версии по отдельности.
5. После подготовительного коммита открыть PR **`Release: 0.4.0-beta.1`** в `santacita-beta`. В diff уже должны быть окончательные версии и заметки. На первом релизе версия исходников уже может совпадать с желаемой: автоматизация всё равно подготовит раздел CHANGELOG.
6. Дождаться проверок и ревью, затем смержить релизный PR.

Локальный эквивалент подготовки: `node packaging/release.mjs prepare`. Сам скрипт ничего не коммитит, не отправляет и не публикует.

## Что происходит после мержа

Только внутренний PR из ветки с точным именем `release/<версия>` запускает создание тега. Обычные PR изменений и инфраструктуры релиз не публикуют.

Workflow сверяет исходники, заметки, номер и целевую ветку. Для `santacita-beta` разрешены только `X.Y.Z-beta.N`, для будущего Rust `main` — стабильные `X.Y.Z`. Тег ставится на коммит мержа. Дальше `build.yml` собирает два DMG, MSI, portable ZIP и AppImage.

После успешной полной матрицы пакеты проходят SHA256/Sigstore-проверку, загружаются в черновик и публикуются как **Pre-release**, без изменения `latest`. Подготовка первого PR ещё не означает, что native matrix и установка на всех ОС уже проверены.

Python 0.3.8 увидит бету только с включённой опцией «Предлагать бета-версии». Без неё пользователи продолжают получать стабильную Python-линию.

## Если сборка упала

Исправить исходники через PR, если ошибка в коде. При временной ошибке повторить упавшие jobs исходного tag-run. Не переносить тег на другой коммит. Опубликованный ошибочный пакет исправляется новой версией.

Если остался черновик, публикация повторно остановится, чтобы не затереть его содержимое. Сначала изучить причину и содержимое черновика. После исправления и удаления незавершённого черновика владельцем можно повторить исходный запуск.

Ручной **Build SantaCita packages** на любой подготовленной Rust-ветке выдаёт артефакты, но не создаёт релиз.

## Что остаётся отдельной проверкой

Установка на каждой целевой ОС, MSI beta.N → beta.N+1 → stable, WebView2 на чистой Windows, portable-перенос, импорт профилей/статистики/секретов и обновление по настоящему опубликованному релизу. До проверки этих пунктов не объявлять миграцию полностью проверенной.
